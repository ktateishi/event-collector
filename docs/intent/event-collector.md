# event_collector — 確定した意図

作成日: 2026-08-07
確定方法: interview-me（1問1答形式のインタビュー、ユーザー明示合意済み）

## Outcome

登録キーワード＋AIで自動拡張した関連語をもとに、複数サイト・SNSを横断探索し、
**日付のあるイベント情報**を毎日スマホにプッシュ通知で **5件** 届ける。

## User

本人1名のみ。共有・マルチユーザー・他人への配信は想定しない。

## Why now

「人から聞いて初めて知った」が繰り返し起きている。潰したい順に:

1. **知らなかった** — 情報の存在自体に到達できていない（最優先）
2. **忘れていた** — 知っていたが受付開始・締切を逃した
3. **気づけなかった** — 情報は目に入っていたが埋もれた

## Success

- 人から聞いて初めて知るイベントが **ゼロ** になる
- 毎朝 **3分以内** で5件を確認し切れる。通知を無視する習慣がつかない

## Constraint

- **1日5件**。内訳は「確実3件＋探索2件」。探索分は「関連の可能性あり」ラベル付きで
  同じ通知に混在させる（別枠にすると見に行かなくなるため）
- 情報源: X / Instagram / YouTube / 公式サイトNEWS欄 / 個人ブログ記事
- **X・Instagram は公式APIを使用し、費用をかけて網羅する**（2026-08-07 決定）。
  非公式スクレイピングによる規約違反・アカウント凍結リスクは取らない。
  想定コストは月2〜3万円規模（詳細: [data-source-feasibility.md](../research/data-source-feasibility.md)）

## 監視モデル（重要な設計判断）

**購読型ではなく探索型を採用する。**

購読型（フォロー先を登録して巡回）は「登録済みの情報源から出た情報」しか守れず、
最優先課題である「知らなかった」＝**未登録の発信元から出た情報**を構造的に取りこぼす。
ユーザーが人から聞いて初めて知るのは、まさにこのケース。

対象キーワードは自分で登録するが、**キーワード自体を知らない穴も妥協しない**。
検索エンジン・生成AIを用いて登録キーワードから関連語を自動拡張する
（制作会社、声優、コラボ相手、シリーズ名、イベント名など）。これは必須要件。

## 含む（「忘れていた」対策）

検知済みイベントについて、受付開始・締切の前に再通知する。

※ この項目はインタビュー中に本人が明言したものではなく、レビュー時に承認された推測。
　 実装前に優先度を再確認する価値がある。

## Web画面の位置づけ（2026-08-07 追記・スコープ拡張）

見逃し防止の主役は引き続き **LINE の毎日5件アラート**（変更なし）。
ただしLINEに届くのは厳選された5件のみであり、それ以外に収集した情報が
「LINEにしか出てこない」状態は避けたい、という要望が追加で確定した。

→ **Web画面は、収集した全件を眺められる場所として必要**
（単なる「5件の詳細確認用の二次画面」より一段広い役割）。
これに伴い、状態保存は Git上のJSONファイルではなく、
**Webサーバーが読み書きする永続データベース**に置き換える
（詳細は [event-collector-spec.md](../spec/event-collector-spec.md) 参照）。

## Out of scope

- 収集・選定の主役をLINEからWebに完全移行すること
  （見逃し防止の一次チャネルはLINEのまま）
- 興味外ジャンルとのランダムな出会い／レコメンド
- 他人との共有・配信・マルチユーザー対応
